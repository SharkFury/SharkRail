# 公共价值设计

状态：用于路线图与贡献决策的项目章程

SharkRail 的使命，是让自治软件能够可预测地执行本地进程。它作为开放、厂商中立的
公共基础设施维护，而不是托管服务或付费产品的获客入口。

协议与可靠性文档定义运行时行为；本文定义项目为何存在、优先服务谁、如何证明公共
价值，以及哪些工作不属于项目。

## 使命

> 让 Agent 的每一次本地执行，都有明确意图、可验证结果和诚实边界。

操作系统本来就能启动进程。SharkRail 只有在显著提高监督可靠性时才有存在价值：输出
排空、终端语义、取消、后代进程清理、有界资源、稳定错误，以及可发现的平台差异。

项目不保证命令必然成功。在已有一致性证据支持的能力范围内，它追求保证调用者能够
判断发生了什么、保留或丢失了什么、尝试了哪些清理，以及当前运行时无法跨越哪些边界。

## 公共价值主张

对于单平台、短时、非交互命令，应直接使用标准库。此时引入 SharkRail 只会增加概念和
故障层。只有当命令执行成为长期产品能力，并出现下列情况时，项目才真正创造价值：

- Windows、WSL、Linux 或 macOS 需要共享一套调用契约；
- 同时需要结构化 Pipe 输出与真实 PTY/ConPTY 行为；
- 任务长时间运行、并发、交互或产生大量输出；
- 超时与取消必须清理运行时拥有的进程树；
- 调用者必须区分“主进程退出”和“输出排空后的真正完成”；
- 资源限制、输出截断、降级清理和不支持能力必须可被机器观察；
- 多个 Agent host 正在重复实现同样的监督代码。

SharkRail 把重复的私有胶水代码转化为四项公共资产：

| 公共资产 | 作用 | 当前状态 |
| --- | --- | --- |
| 开放执行契约 | 稳定定义生命周期、事件、错误、限制与 capability | 已有协议、schema 与可靠性契约 |
| 平台原生参考实现 | 用真实系统机制证明契约可以实现 | Python alpha 已有 Windows/POSIX backend 与 WSL 路由；保证覆盖范围必须由公开状态矩阵说明 |
| 跨实现一致性套件 | 让客户端和替代运行时证明行为兼容 | 已有内部测试，但可独立运行的套件仍是路线图重点 |
| 共享失败语料库 | 把挂起、后代残留、输出丢失、编码和平台差异变成可复用回归资产 | 测试中已有案例，但仍需形成具名、可检索的语料库 |

即使其他实现通过公开一致性套件，客户端可以替换掉 Python 参考运行时，项目依然成功。
契约被采用是公共价值；锁定到单一实现不是。

## 差异化必须被证明

进程 API、易用型 subprocess 封装、PTY/ConPTY 库、进程树工具和 Agent 终端协议，已经
解决了这个问题的许多部分。SharkRail 不应把创建进程、JSON-RPC、PTY 分配或 Job Object
描述成自己的发明。

相关项目包括 [Execa](https://github.com/sindresorhus/execa)、
[ProcessKit](https://github.com/ZelAnton/ProcessKit-rs)、
[node-pty](https://github.com/microsoft/node-pty)、
[pywinpty](https://github.com/andfoy/pywinpty)、
[portable-pty](https://github.com/wezterm/wezterm/tree/main/pty)，以及
[ACP terminal contract](https://agentclientprotocol.com/protocol/v1/terminals)。SharkRail 应在
可能时复用、互操作或向上游贡献，并坦率说明能力重叠；任何比较性主张都必须附带可复现
fixture 或 benchmark。

项目真正可成立的公共贡献，必须是“领域语义 + 可移植黑盒证明”的组合：退出与输出排空
完成严格分离、字节级损失记账、可观察的取消升级、经过验证的 containment，以及明确的
Windows/WSL 边界。通用 Agent transport 与 task 语义应映射 ACP、MCP 等现有标准，而不是
与它们竞争；原生库应保持为可替换的 backend 构件。

在出现与实现无关的一致性套件和独立采用者之前，SharkRail wire protocol 只是项目契约，
不是行业标准。文档必须始终保留这个区别。

## 受益者与核心任务

| 优先级 | 受益者 | 核心任务 | 价值证据 |
| --- | --- | --- | --- |
| 首要采用者 | Agent、IDE、自动化运行时维护者 | 用一套明确会话契约替代重复的 subprocess、PTY、缓存、deadline 与清理代码 | 接入胶水减少；失败可分类；同一测试通过多个目标平台 |
| 首要权利相关者 | 允许 Agent 操作本机的人 | 对执行进行限制、观察、取消和诊断，不发生隐藏丢失或遗留受控进程 | 限制与取消可见；诊断不暴露秘密；平台边界明确 |
| 生态实现者 | Client、adapter、SDK 与 backend 作者 | 复用或实现契约，而不复制监督逻辑或依赖某一家 Agent 厂商 | adapter 保持轻薄；独立组件通过一致性 fixture |
| 社区贡献者 | 系统程序员、CI 作者与故障报告者 | 把一次真实故障转化为最小复现和永久回归资产 | 可复现报告进入文档、fixture 与测试 |

Agent 是机器消费者，但机器所有者是最重要的权利相关者。Agent 的便利不得凌驾于用户
控制、隐私和真实报告之上。

## 价值优先级

目标冲突时，按以下顺序决策：

1. 用户控制、隐私与诚实的安全边界；
2. 生命周期正确性、有界行为与输出完整性；
3. 平台能力与降级情况的真实表达；
4. 协议互操作性与兼容性；
5. 接入简单度与诊断质量；
6. 功能与 adapter 数量。

一个能力较少但可以证明的运行时，比一个无法证明完成与清理行为的“大而全”运行时更
有价值。

## SharkRail 替代什么，不替代什么

| 替代方案 | 适用场景 | SharkRail 的关系 |
| --- | --- | --- |
| `subprocess`、`asyncio` 或平台进程 API | 单平台、短时、非交互、单应用可控命令 | 除非监督故障足以证明额外运行时的必要性，否则不要替换 |
| pywinpty、portable-pty 等 PTY 库 | 主要需求只是打开和驱动终端 | 在其上补充生命周期、限制、事件和协议语义 |
| 终端应用与复用器 | 人类需要查看和操作终端 | 与之互补；SharkRail 不提供终端 UI |
| 容器、虚拟机、AppContainer、Windows Sandbox | 不可信代码需要隔离 | 与之组合；SharkRail 不是安全沙箱 |
| CI 与工作流引擎 | 需要编排、持久调度、重试或分布式 worker | SharkRail 位于其下层，只负责本地执行 |
| host 专用 exec server | 单一产品与平台需要高度定制行为 | 只有共享契约和跨平台维护产生明确收益时才迁移 |

## 永久范围护栏

SharkRail 不会变成：

- 通用 Agent 框架、规划器、工具市场或工作流引擎；
- 托管执行云、远程 Shell 或多租户计算服务；
- 恶意代码沙箱、凭据保险箱或权限提升系统；
- 终端模拟器 UI 或面向人类的完整终端产品；
- 依靠 Prompt、颜色或正则表达式判断完成的工具；
- 隐藏真实操作系统差异的最小公分母 API；
- 把厂商专属行为塞进执行核心的集成集合；
- 为替换一个本来已经工作的标准库调用而存在的抽象层。

Agent 协议属于 adapter，厂商专属行为属于核心之外。无法明确有界完成条件、可观察
失败、平台行为和维护责任的功能，不进入运行时核心。

## 开源公共维护承诺

SharkRail 官方项目按照公共基础设施的原则维护：

- 运行时、协议、schema、一致性资产、文档和正常开发过程保持公开；
- 路线图以共享可靠性和互操作性为目标，而不是收入、云转化或付费客户特权；
- 不设官方私有版本、核心能力付费墙、强制账户或必需的托管控制面；
- 默认保持本地优先，不要求远程遥测；
- 除安全报告所需的暂时保密外，重要技术与治理决策公开进行；
- 如果未来接受赞助或资助，必须公开披露，且不得购买协议结果、发布决定、维护者身份或
  私有路线图。

SharkRail 使用 MIT License。该许可证允许个人和公司商业使用、修改、打包与支持软件。
以上承诺约束官方项目的发展方向，不是额外的许可证限制，也不削减使用者自由。

## 用证据而不是主张证明价值

项目的北极星指标是：

> 在受支持的平台与 backend 组合上，被消除且得到验证的真实执行故障类型。

项目围绕四组证据维护公开价值记分板。Star、下载量、代码行数、adapter 数和功能数只能
说明传播情况，不能证明价值。

### 1. 契约正确性

- 每个适用平台/backend 通过的已知回归 fixture；
- 运行时造成的无界等待：目标为零；
- 静默输出丢失与无法分类的终态：目标为零；
- 成功清理后仍残留的受控后代进程：在已声明平台边界内目标为零；
- capability 声明与实际探测行为不一致：目标为零；
- 每条有界损失、deadline 与降级清理路径均有结构化结果。

### 2. 互操作性与采用质量

- 仓库之外被真实使用的独立 Agent、IDE 与自动化集成；
- 完成参考接入所需时间和 host 专属胶水代码量；
- 通过一致性套件的独立客户端或运行时；
- 兼容升级后无需修改仍能工作的客户端；
- 一次核心修复同时让多个 host 或 adapter 获益的案例。

### 3. 社区可持续性

- 外部故障报告转化为最小 fixture 和回归测试的数量；
- 具有独立组织背景和不同平台经验的 reviewer/maintainer；
- 附带公开理由、兼容分析和迁移说明的重大决策；
- 文档、schema、示例与实现之间尚未关闭的不一致；
- 关键平台是否有熟悉其原生语义的活跃 reviewer。

### 4. 用户主权与信任

- 默认运行时要求的网络调用与远程遥测：零；
- 默认日志和诊断包的敏感信息泄露：目标为零；
- 输出损失、资源干预和 capability 降级全部显式报告；
- 所有公开破坏性变更均附迁移说明和兼容测试。

公开测量必须包含测试环境、迭代次数、失败定义、已知盲区和原始复现步骤。没有边界说明
的绿色徽章不是充分证据。

### 当前 alpha 的证据边界

当前仓库已经对会话生命周期、Pipe 与 POSIX PTY、有界输出、读取游标、超时、协议路径
以及 MCP/ACP 正常集成路径建立了有意义的测试；Windows backend 与 Job Object 也有实际
代码，并非仅存在于文档。

但这还不是可移植的一致性证据。Windows 原生后代清理与 ConPTY 压力路径需要更强的
非 Mock 测试；WSL 的路由证据强于清理证据；资源限制需要真实 workload 验证；长时间
竞态、泄漏与性能基线也尚未公开。这些缺口是发布工作，不能藏在 CI badge 后面。

## 工作准入测试

每个功能提案必须回答：

1. 哪类用户遇到了什么可复现的执行故障，频率如何？
2. 为什么标准进程 API、PTY 库或已有组合不能充分解决？
3. 它属于共享核心契约、平台 backend、adapter，还是示例？
4. 调用者会得到什么机器可观察结果、错误、资源边界和完成规则？
5. 哪个 fixture、故障注入或一致性测试能够证明价值？
6. 各平台的原生语义与诚实降级分别是什么？
7. 对隐私、权限、供应链和兼容性有什么影响？
8. 谁维护该行为及其平台测试？
9. 它应该改善哪个公共价值指标？
10. 如果证据不成立，如何弃用或移出核心？

提案最终只能进入五个位置之一：核心契约、平台 backend、adapter、示例/配方、拒绝或
延后。不能仅仅因为“可以实现”就进入核心。

下列情况应立即阻止进入核心：隐式 Shell 解析、静默降级、无界资源或等待、暗示安全
沙箱能力、把核心绑定到单一 Agent 厂商，以及缺少兼容和测试策略。

## 社区价值循环

```text
真实故障报告
    -> 最小复现
    -> 具名跨平台 fixture
    -> 契约澄清
    -> 参考实现修复
    -> 一致性回归
    -> 文档与采用者反馈
```

代码只是其中一种贡献。故障报告、Windows/WSL 复现、测试 fixture、文档、翻译、评审与
集成报告，都是一等贡献。

## 成熟路径

成熟度由证据获得，不由日期或功能数量决定。

### 可信

- 只有一套权威且内部一致的已发布状态文档；
- 建立覆盖生命周期、输出、取消、PTY 与平台特有行为的具名失败语料库；
- 发布带有界压力与故障测试的跨平台记分板；
- 每项对外保证都链接到测试，或明确标注为限制。

### 有用

- 参考集成证明 host 不需要复制监督逻辑即可采用契约；
- 独立用户贡献可复现案例和公开集成报告；
- 升级具有明确的兼容测试与迁移路径。

### 基础设施

- 一致性套件可以脱离 Python 参考实现独立运行；
- 至少两个独立维护的客户端或运行时通过套件；
- 治理、评审和发布权限不再依赖单一个人或组织。

路线图应按这个顺序前进：先证明契约，再降低采用成本，再让契约可以被独立实现，最后
才扩展功能广度。
